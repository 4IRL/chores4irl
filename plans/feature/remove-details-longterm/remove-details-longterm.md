# Remove *Details* and *Long-term task* fields (F4)

## Summary
Delete the *Details* text field and the *Long-term task* checkbox from the chore form and propagate the removal through the shared `Chore` type, the backend data-access layer (`createChore` + `updateChore` + row mapping), the SQLite schema and seed, and the frontend sort util — which currently pins long-term chores to the bottom of the list and collapses to a single duration-weighted sort. Because `db.ts` has no migration framework and an existing `data.db` (dev checkouts and the Pi's Docker volume `/data/data.db`) is *not* altered by editing the `CREATE TABLE` text, this feature introduces the repo's first migration: an idempotent, `pragma table_info`-guarded `ALTER TABLE chores DROP COLUMN` pair that runs at module load between `CREATE TABLE IF NOT EXISTS` and the seed block, inside a `BEGIN IMMEDIATE` transaction, and that deliberately aborts boot (crash loud, no try/catch) if a `DROP` fails. The backend lands in two independently green steps — data access first (its trimmed SQL works against both the legacy and the migrated schema), schema + migration second — so no step boundary leaves POST/PUT broken. `urgency` is retained. F3-L (Room datalist) and F14 (clear-✕ on Name/Room/search) wiring is left byte-for-byte untouched.

- **Migration is empirically verified** on the bundled better-sqlite3 12.8.0 / SQLite 3.51.3 (≥ 3.35 → `DROP COLUMN` supported; better-sqlite3 12.8.0's install script is `prebuild-install || node-gyp rebuild`, and both the upstream `linux-arm64` prebuilt and a source build embed the package's bundled `deps/sqlite3/sqlite3.c` = 3.51.3, so the Pi runs the same version — the lockfile pins 12.8.0 and `Dockerfile.backend` uses `npm ci`): `ALTER TABLE chores DROP COLUMN details` and `… DROP COLUMN long_term_task` both succeed on the exact legacy 9-column schema (the `NOT NULL DEFAULT 0` and the sibling `CHECK(urgency IN …)` are not blockers), rows keep all other values, `AUTOINCREMENT` continues, WAL needs no special handling. A second unguarded `DROP` throws `SqliteError: no such column: "details"` at module load — which would fail the Docker `HEALTHCHECK` and wedge the Pi stack in its `restart: on-failure:5` loop — so the `pragma table_info('chores')` guard is mandatory, and it is read **inside** a `db.transaction(...).immediate()` (`BEGIN IMMEDIATE` takes the write lock before the pragma read, so two processes booting the same un-migrated file — e.g. a dev server and `db-path.test.ts` case 3 — serialise instead of the second throwing `no such column`; a busy first booter surfaces as `SQLITE_BUSY`). Verified against a file-backed WAL database: two consecutive calls of the exact Step 2 function → 7 columns, the row intact, the second call issues zero `ALTER`s and does not throw. `db.pragma("table_info('chores')")` returns `Array<{cid,name,type,notnull,dflt_value,pk}>` (do **not** use `{ simple: true }`). `CREATE TABLE IF NOT EXISTS` with the new 7-column text is a no-op against a legacy table, so the order must be CREATE → migrate → seed.
- **The trimmed data-access SQL is schema-agnostic.** Verified on better-sqlite3 12.8.0 against the exact legacy 9-column table: a 5-column raw `INSERT INTO chores (name, room, date_last_completed, duration, frequency)`, the new 6-column named-param `INSERT … urgency) VALUES (… @urgency)`, and the trimmed `UPDATE chores SET … urgency = @urgency WHERE id = @id` all succeed (`details` is nullable, `long_term_task` is `NOT NULL DEFAULT 0`). This is why `chores.ts` can be de-referenced **before** the schema changes (Step 1) with every backend test green, why from Step 1 onward the runtime app works against both schemas, and why the rollback asymmetry in Step 8 runs one way only (new code on an old DB is fine; old code on a migrated DB is not).
- **Migration test pattern already exists.** `backend/src/__tests__/db-path.test.ts` uses `mkdtempSync` + `vi.resetModules()` + `delete process.env.DB_PATH/TEST_DB_PATH` + `process.env.DB_PATH = <tmp file>` + `await import('../db.js')`. Its third case opens the **real** repo-root `data.db`, so the first `npm test --workspace backend` after Step 2's `db.ts` edit runs the migration against a developer's dev DB (stop `npm run dev --workspace backend` first to avoid `SQLITE_BUSY` on the one-time `ALTER`).

Long-term chores (in seed: only the HVAC row) will interleave by `duration × overdue-fraction` instead of being pinned last. `choreSort.test.ts` 'separates short-term from long-term chores' asserts the old rule and must be replaced; App.test.tsx's 'frozen sort order' suite uses no long-term chores and is unaffected.

## Decisions resolved during planning
- **(a) SQLite ≥ 3.35:** confirmed 3.51.3 → `DROP COLUMN` path; no table-rebuild fallback needed.
- **(b) Fully delete `details`:** yes — column dropped, no archival. The seed's HVAC description is the only known non-null value. Any user-entered Details text on the Pi is dropped irreversibly by the migration (recoverable only from the pre-deploy snapshot) — see the inspection step in Step 8.
- **(c) Pi live `data.db`:** migration fires on first backend container start after redeploy (`docker-compose.yml` `DB_PATH=/data/data.db`, named volume `chores-data`). Pre-deploy: take one snapshot via `sudo systemctl start chores4irl-backup.service` (the unit supplies the mandatory `BACKUP_RSYNC_DEST`; invoking `bin/chores4irl-backup.sh` directly exits 1 unless `BACKUP_RSYNC_DEST` — and, off the default Pi layout, `COMPOSE_FILE` — are exported; README "Backup strategy"). Verification is manual/unsandboxed (LAN unreachable from sandbox) — see Step 8.
- **(d) `PUT`/`updateChore` fully de-referenced:** yes — Step 1 covers both the SQL `SET` list and the named-param literal; Step 1's `routes.test.ts` stale-key PUT test asserts the response carries neither key.
- **Backend step order: data access before schema.** `chores.ts` is de-referenced first (Step 1) because its trimmed SQL works against both schemas (Research Findings bullet 3); the schema/migration/seed lands second (Step 2). Every step boundary is green and independently committable, and from Step 1 onward the app works against both the legacy and the migrated schema — the property Step 8's rollback runbook relies on.
- **Migration shape:** export a pure `dropLegacyChoreColumns(db)` from `db.ts` and call it at module load (hybrid: unit-test the function twice in-process on `:memory:` for idempotency, plus one boot test against a legacy temp file to prove wiring). Two separate `ALTER` statements (SQLite has no multi-column `DROP`) inside one `db.transaction(...).immediate()`, with the `pragma table_info` read inside the transaction so the guard and the `DROP`s happen under the same write lock.
- **Migration failure policy: crash loud.** No try/catch around the `DROP`s. Verified that the new INSERT/UPDATE also work against the legacy schema, so a logged-and-tolerated failure would leave a fully functional app on 9 columns — tolerating is viable, but a loud failure is preferred: a thrown `ALTER` aborts boot before `listen`, the Docker `HEALTHCHECK` never passes, and `restart: on-failure:5` stops the stack after five tries, which is impossible to miss on the kiosk. Step 8's runbook step 4 already directs the operator to `docker compose logs backend` when the frontend never comes up (also surfaced in the README Pi-update caveat, Step 5).
- **META-PLAN F4 "Expected end state" bullet 1 is unsatisfiable as written** (`grep … returns no matches` — the migration's own `ALTER … DROP COLUMN long_term_task` and the META-PLAN-required idempotency test must name the columns). META-PLAN's F4 section (line 512) is not edited on this branch — the only META-PLAN diff on the branch is the F4 Status-ledger row that `/run-feature` Phase A steps 3/10 own; leave that diff in place and let it ride in the first commit. The reconciled wording is recorded in Step 6 and the PR description, for `/run-feature` Phase C to fold into META-PLAN.
- **`frontend/src/assets/database.ts`:** delete the file (zero importers; its own comment says it is kept only as reference and is superseded by `backend/src/db.ts`).
- **'Details field never renders a clear-✕' test:** replace with an explicit removal-regression test (`queryByLabelText('Details')` and `queryByLabelText('Long-term task')` both `null`) — the negative guarantee for non-clearable `FormField`s already lives in `FormField.test.tsx`.

    // F4 migration: drop the legacy `details` / `long_term_task` columns from databases created
    // before their removal. `CREATE TABLE IF NOT EXISTS` never alters an existing table, and an
    // unguarded DROP COLUMN throws "no such column" on the second boot — so guard on
    // pragma table_info. Requires SQLite >= 3.35 (better-sqlite3 bundles 3.51.3).
    // BEGIN IMMEDIATE takes the write lock before the pragma read, so two processes booting the
    // same un-migrated file serialise instead of the second throwing "no such column"; a busy
    // first booter surfaces as SQLITE_BUSY.
    // A failed DROP aborts boot on purpose (no try/catch): the compose stack stops after 5
    // restarts, and the PR runbook tells the operator to check `docker compose logs backend` if
    // the frontend never comes up.
    const LEGACY_CHORE_COLUMNS = ['details', 'long_term_task'] as const;

    export function dropLegacyChoreColumns(target: Database.Database): void {
        target.transaction(() => {
            const present = new Set(
                (target.pragma("table_info('chores')") as { name: string }[]).map(c => c.name),
            );
            for (const col of LEGACY_CHORE_COLUMNS) {
                if (present.has(col)) target.exec(`ALTER TABLE chores DROP COLUMN ${col}`);
            }
        }).immediate();
    }
