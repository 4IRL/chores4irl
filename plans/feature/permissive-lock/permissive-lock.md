# Permissive touch lock (F20)

## Summary
Rework the shipped `F2` touch lock so it guards only *destructive* actions. While locked, the app root is no longer `inert` (only screen-blank keeps that gate). Completing, editing or deleting a chore surfaces the padlock overlay instead of acting, seeded with the blocked tap as the *first* tap of the unlock double-tap. Everything else keeps working while locked: scrolling, `F18`'s scroll-to-top button, search, room tabs, day simulation, and *Add Task* including its submit. The top-left `TouchLockIndicator` becomes a ≥ 44 px lock/unlock button. `useTouchLock`'s inactivity timer keeps running while locked and exposes an idle tick, and `F19`'s lock-time view reset re-keys to that tick (closing an Add modal left open under the lock first). Source of truth: `plans/META-PLAN.md` § "F20 — Permissive touch lock" plus Standing invariants 9 and 17–19.

## Research Findings
- **One consumer chain per symbol.** `useTouchLock` → `App.tsx:41` only. `TouchLockOverlay` and `TouchLockIndicator` render twice in `App.tsx`: in the loading branch (`:349-365`) and the main branch (`:367-455`). - **Spec gaps found in research (resolved below):**
  - (1) `ChoreTimerBar`'s sr-only **"Edit chore"/"Delete chore" keyboard buttons** (`:133-151`) call `onEdit`/`onDelete` directly. Once the root is no longer inert they become a way to edit or delete under the lock, so they must be guarded too.
  - (2) A **vertical drag ≥ 50 px** over a bar also fires `onSwiping`/`onSwiped` (dir `Up`/`Down`). A naive swipe guard would show the padlock while someone scrolls, so the guard fires only for `Left`/`Right`.
  - (3) After a swipe the browser fires a **trailing click**. The locked `onSwiping` must still set `swipingRef` so `resetTask` swallows that click; otherwise the guard fires twice per gesture.
  - (4) **`e2e/smoke.spec.ts`'s F2 test (`:383-555`) exercises the lock.** It expects the overlay right after `fastForward('05:01')` (`:400`) and expects *Add Task* blocked while locked (`:476-486`). Both invert under F20, so the META-PLAN's "none expected" note is wrong and the test is rewritten here, in the same step as the behavior change.
  - (5) A 44 px indicator at `top-2 left-2` would cover the *All* room tab. The user chose (2026-09-24) to reserve a left gutter: `NavBar`'s root goes from `px-4` to `pl-14 pr-4`.
- **`react-swipeable` 7.0.2** gives `eventData.initial: [x, y]`, the touchstart/mousedown `clientX`/`clientY` in the same coordinate space as the overlay's `event.clientX/Y`. That is the swipe's seed point (Open risk (a)). A movement under `delta: 50` is a tap and goes through the `onClick` path.
- **Test infrastructure.** Vitest 4.1.4 + jsdom 29 + RTL 16. Run with `cd frontend && npx vitest run <file>`; the baseline is 40 files / 397 tests green. Lint is `npm run lint`; typecheck is `npx tsc --noEmit -p frontend/tsconfig.json` (test files are typechecked). Use `fireEvent` (not `userEvent`) whenever a test depends on the timer.

### Decisions (resolving META-PLAN F20 Open risks (a)–(g) and the gaps above)
- **(a) Swipe seed:** `{ x: eventData.initial[0], y: eventData.initial[1] }`, fired once from `onSwiped` and only when `dir` is `'Left'`/`'Right'` (any horizontal swipe counts as an attempt, even below the 25 % threshold). A tap uses the click's `clientX`/`clientY`. The sr-only buttons use the click's `clientX`/`clientY`, which keyboard activation reports as `(0, 0)`. That matches the overlay's keyboard path, which registers `(0, 0)`, so a keyboard attempt followed by Enter/Space on the overlay unlocks.
- **(b) Add form on lock engage:** the default stands. A lock engage (idle *or* manual, via the indicator) closes an open Add form through the existing force-close effect. Each later idle tick while locked also closes it (step 0 of the re-keyed `F19` effect).
- **(c) Dialogs reachable while locked:** only the Add modal. Edit and delete (swipes *and* sr-only buttons) are guarded, so `ConfirmDialog` and the edit modal cannot open under the lock. Both are also gated in JSX on `!isLocked` (DD-14): the force-close effect clears their state one passive-effect later than the idle engage commits, and with the root no longer inert that gap would leave a still-mounted `ConfirmDialog`/edit modal clickable. The force-close effect still clears `pendingDeleteId`/`editingId`, so nothing reappears on unlock. The Add form stays ungated (it is allowed while locked; the engage-time force-close still closes it). The existing `(e)` auto-dismiss tests cover the gate.
- **(d) Overlay mount strategy: mount-on-attempt.** `App` holds `lockAttempt: { id: number; point: TapPoint } | null`. The overlay renders with `key={lockAttempt.id}` and `firstTap={lockAttempt.point}`, starts in `'awaiting-second-tap'` with no entrance animation (the 600 ms `justRelocked` fade is deleted), and focuses itself on mount (keeping the keyboard path).
  - **Opening swallows taps (DD-21):** after a qualifying tap the overlay's root stays hit-testable through its 400 ms `'opening'` animation (no `pointer-events-none` in `'opening'`), and `registerTap`'s existing `'opening'` early return discards what it catches. So a rapid third tap within ~0.4 s of the unlock is swallowed rather than completing the chore beneath; tapping again after the padlock has gone completes it.
  - **Fade-out (DD-2), matching META-PLAN's "fades after the window":** when `SECOND_TAP_WINDOW_MS` (1500 ms) elapses with no qualifying tap, the overlay enters a new `'dismissing'` phase. Its root goes `opacity-0 pointer-events-none` under a `transition-opacity duration-[400ms]` (the same 400 ms the centred padlock's `duration-[400ms]` pairs with `CLOSING_SETTLE_MS`), taps pass through to the board beneath (the root is `pointer-events-none`) while keys reaching the still-focused overlay are ignored (as in `'opening'`), and it calls a new `onDismiss` prop `CLOSING_SETTLE_MS` later, i.e. 1900 ms after the last first tap. `App` then clears `lockAttempt`. Taps during the fade fall through to the still-locked board: a bar tap raises a fresh attempt (new `key`, full opacity, seeded at that tap — so a late second tap at 1.5–1.9 s re-shows the padlock rather than unlocking), the corner indicator unlocks, and everything else acts normally.
  - **Far taps (DD-1), kept as `F2`:** the overlay is full-viewport, so while it shows (awaiting) every tap is swallowed, except one on the raised corner indicator (DD-22), which unlocks. A tap more than 60 px from the first tap becomes the new first tap and restarts the window, so the padlock stays up until ~1.5 s after the *last* tap and only then fades. Pinned by the `>60 px away becomes a new first tap` unit test; see Manual checks.
  - **Stale closing timer (DD-4, accepted):** `handleArm`'s `CLOSING_SETTLE_MS` timer clears whatever `lockAttempt` is current when it fires. A new attempt made within 400 ms of an unlock (it needs the unlock, a manual re-lock from the indicator and a bar tap all inside 400 ms) is therefore cleared early. That is non-destructive (the bar stays guarded; the next tap raises the padlock again), so it is accepted.
- **Simulation wins over the lock (DD-7):** while `isSimulating`, bar taps and swipes do nothing (no padlock). The bar is `pointer-events-none` and the handlers return on `isSimulating` first. The indicator is the only unlock. The sr-only Edit/Delete pills have no `isSimulating` check today, so while locked and simulating a keyboard activation still raises the padlock; that asymmetry is accepted.
- **(e) `F18` interplay:** none. The guard sits in the bar's own handlers, and the scroll-to-top button reads no lock state.
- **(f) pi-kiosk:** no pi-kiosk file is touched. The META-PLAN F2 kept contract is rewritten to this as-built shape for `F15`.
- **(g) Accessibility:** the indicator is a `<button type="button">` with `aria-label` `"Lock screen"`/`"Unlock screen"` flipping with state, a `focus-visible:ring-2 focus-visible:ring-indigo-400` ring, and an `aria-hidden` icon. The overlay hands focus back (DD-6), guarded (DD-15): its mount effect captures the overlay node and the previously focused element before focusing itself. On unmount it restores that element only if it is still connected **and** focus is still on the overlay or nowhere (`document.activeElement` is `null`, `document.body` or the overlay node). A keyboard user therefore returns to the sr-only pill that raised it, but focus the user moved elsewhere meanwhile (the Add form's `autoFocus` Name field, a Tab to the indicator, a click on the raised indicator) is never stolen back. StrictMode's dev double-mount is harmless: at the simulated cleanup the overlay node still holds focus, so it restores the original element before the effect re-runs, and the re-run captures that same element again (verified in-repo with a scratch Vitest harness under `<StrictMode>`).
- **Indicator z-order (DD-5, DD-22):** the indicator is `z-40`, below the `z-50` modal backdrops. An open modal's backdrop covers the corner, so a corner tap cancels the modal as before and never toggles the lock. While locked with the Add form open, the corner can't unlock until the form closes (accepted).
  - **Raised while an attempt shows (DD-22):** `TouchLockIndicator` takes an optional `raised?: boolean` (default `false`) that swaps `z-40` for `z-[95]` (above the `z-[90]` overlay, under the `z-[100]` blank). `App`'s main branch passes `raised={lockAttempt !== null}`, so while the padlock shows (awaiting, fading or opening) a single corner tap reaches the indicator. While locked it unlocks through `handleIndicatorUnlock` (DD-3), whose path is now reachable by pointer, not only by keyboard.
  - **Accepted interactions:** a pointer attempt can't coexist with an open Add modal (the bars sit under its `z-50` backdrop). A keyboard sr-only-pill attempt made while the Add form is open raises the indicator above that backdrop, so the corner then unlocks rather than cancelling the form. During the 400 ms `'opening'` animation the app is already unlocked, so a corner tap there re-locks (the indicator's normal unlocked behavior), and the force-close effect then drops the attempt.
- **Idle tick semantics:** `idleExpiries` counts **every** inactivity expiry, including the one that engages the lock. The expiry callback re-schedules itself, so while locked with no activity it ticks every `INACTIVITY_MS`. Activity (`pointerdown`/`keydown`, now listened for while locked too) postpones the next tick. `lock()` engages immediately and restarts the countdown without bumping `idleExpiries`; its `false → true` flip re-runs the `F19` effect by itself. `arm()` is unchanged.
- **Blank precedence:** the overlay renders only when `!isBlanked`. The force-close effect also clears `lockAttempt`, so a pending attempt never reappears after a wake.
- **Loading branch:** no bars exist there, so no attempt can occur. It keeps the indicator and the blank overlay and drops `TouchLockOverlay`.
