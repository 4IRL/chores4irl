# Translucent / blur Add Task deck (F5)

## Summary
The bottom *Add Task* deck in `frontend/src/App.tsx` becomes a frosted-glass surface: a semi-transparent `bg-gray-900/60` background with `backdrop-blur-sm`, so chore bars are faintly visible as they scroll beneath it. Today the deck is an opaque flex sibling *after* the scroll area, so nothing ever sits behind it — to make the blur meaningful the deck moves *inside* the scroll container as a `sticky bottom-0` element pushed to the bottom with `mt-auto`. The deck stays pinned to the bottom of the viewport in every list length (empty, short, overflowing); at max scroll the last bar rests fully above the deck, so nothing tappable is ever hidden at rest. `AddChoreButton` becomes fully opaque (`bg-blue-500`), per the F5 open-risk default in `plans/META-PLAN.md`. Purely CSS/JSX-structure — no JS behaviour change, no e2e change.

## Research Findings
- **The deck is not an overlay today.** `App.tsx:318` is the opaque `bg-gray-900` flex column (`px-4 pt-4`, no `pb-*`); `App.tsx:334` is the only scrolling element mounted in the base App tree — the whole `html/body/#root/.App` chain is `overflow: hidden` by design (`index.css:4-17`, `App.css:1-8`); `ChoreForm.tsx:75` has its own `overflow-y-auto max-h-[90dvh]`, but it lives in `ChoreFormModal`'s separate `document.body` portal, is mounted only while the form is open, and so never interferes with `document.querySelector('.overflow-y-auto')`; `App.tsx:337` is the deck, a normal-flow `flex-shrink-0` sibling *after* the scroll area with no `bg-*`/positioning of its own. Translucency alone would reveal nothing; the scroll content must extend under the deck. No `sticky` exists anywhere in `frontend/src` yet; `relative` + `absolute` idioms exist only within single components (`ChoreTimerBar.tsx:96/104/108`, `ChoreSearchInput.tsx:15/17`).
- **Chosen layout technique — sticky-in-scroller, zero magic numbers.** The scroll container gains `flex flex-col`; the deck moves inside it as its last child with `sticky bottom-0 mt-auto`. `mt-auto` pins it to the bottom when the list is short/empty; `sticky` pins it while overflowing content scrolls beneath; at max scroll the deck occupies its own in-flow slot after `ChoreList`'s existing `pb-4` (`ChoreList.tsx:24`) so the last bar is fully clear of it. Note for Phase C: META-PLAN F5's Expected-end-state bullet "Deck remains pinned at the bottom (`flex-shrink-0`)" names today's mechanism; this plan keeps the `flex-shrink-0` token but the pinning mechanism becomes `sticky bottom-0 mt-auto` — the fold-back should update that parenthetical rather than copy it verbatim. Rejected alternatives: absolute-positioned deck + `pb-<deck height>` clearance on the list, or a negative-margin overlap — both hard-code the deck's rendered height (≈81px: `py-4` 32 + button 48 + border 1) and silently break reachability if the button ever resizes.
- **Hard test constraint.** `frontend/src/__tests__/App.search.test.tsx:236` does `document.querySelector('.overflow-y-auto')` and asserts the search input is *outside* it and `ChoreList` content is *inside* it. The literal `overflow-y-auto` token must stay on `App.tsx:334`, no earlier element may gain it, and `ChoreSearchInput` must remain outside. Moving the deck inside the scroll region is compatible.
- **Hit-testing / e2e risk (real: seed has 10 chores, `backend/src/db.ts:39-50`, which overflows Playwright's 1280×720).** `ChoreTimerBar.tsx:117-123` attaches `react-swipeable` to the bar itself; `e2e/smoke.spec.ts:220-248` `swipeBar()` calls `scrollIntoViewIfNeeded()` then drives raw `page.mouse` at `boundingBox()` coordinates. A bar that is geometrically inside the scrollport but visually under the sticky deck would receive the deck's DOM element on pointer-down. Mitigation: `scroll-pb-24` (`scroll-padding-bottom: 6rem` = 96px, giving 15px headroom over the ≈81px deck. Chrome aligns a Tab-focused element's *own* rect — the 28px sr-only pill — not its 64px bar, to the scroll-padding edge, so an 80px value left the pill's bottom row 1px under the deck's `border-t` — measured in Step 3 run 1; the max-scroll last bar still sits inside the reduced snapport: bottom 623 ≤ 624 at 1280×720, 927 ≤ 928 at 768×1024) on the scroll container declares the deck's footprint as obscured, so `scrollIntoView` / `scrollIntoViewIfNeeded` (CDP's centre-if-needed uses the scroll-padding-reduced snapport) and keyboard focus on the sr-only edit/delete buttons (`ChoreTimerBar.tsx:137/146`) all land bars above the deck. The deck deliberately keeps default pointer events — a frosted surface should *not* pass taps through to half-hidden bars (`pointer-events-none` was considered and rejected).
- **Stacking is a non-issue.** `ScreenBlankOverlay`/`TouchLockOverlay` `createPortal` to `document.body` (`fixed`, `z-[100]`/`z-[90]`); `TouchLockIndicator` renders inline at `App.tsx:317` but is likewise `fixed z-[80]`; modals are `fixed inset-0 z-50` portals. The deck needs no z-index — as a positioned (sticky) element later in DOM order it paints above the bars' `relative`/`absolute` (z-auto) layers. `backdrop-blur-sm` + `bg-black/60` is already shipped on `ConfirmDialog.tsx:26` and `ChoreFormModal.tsx:22`, so `backdrop-filter` *rendering* support on the Pi's Chromium is proven, and the deck's blur area (≤768×81px) is far smaller than those full-viewport scrims. That closes the rendering half of META-PLAN F5's "confirm `backdrop-blur` performs acceptably on the Pi" risk for the PR; the scroll-smoothness half (those scrims blur a static backdrop, the deck blurs content moving beneath it) is answered only by the post-merge check — the sandbox cannot reach the Pi (loopback-only netns — see memory `sandbox-cannot-reach-pi-lan`), so as a **non-blocking post-merge follow-up** the user eyeballs scroll-blur smoothness on the kiosk after the normal redeploy, and Phase C records that in META-PLAN. Tailwind is v4.1 CSS-first (`index.css:1` `@import "tailwindcss"`); `frontend/src/tailwind.config.js` is dead (eslint-ignored, no `@config`) — new utilities need no config edits.
- **Button opacity decision (explicit).** `AddChoreButton.tsx:8` is `bg-blue-500/50 hover:bg-blue-600/50`, locked by `AddChoreButton.test.tsx:9` ("renders a translucent blue button" — a Tailwind-v4-migration guard preserving the pre-existing look, not an F5 design choice). `META-PLAN.md` F5 "Open risks / decisions" resolves this as *default: translucent+blurred deck, fully opaque button*, and its cumulative-invariants line reads "opaque button". This plan follows that default: `bg-blue-500 hover:bg-blue-600`, and updates the unit test to assert the opaque form (keeping the dead-`bg-opacity-50` guard). Reviewer: if the muted translucent blue is preferred, drop step 1b/2b — the deck change is independent.

Class-assertion precedent: `AddChoreButton.test.tsx:9-12`, `ProgressBar.test.tsx:11-15` (`className.toContain`). `App.test.tsx` renders the real `<App/>` with `services/choreApi` + `useMidnightClock`/`useScreenBlank`/`useTouchLock` mocked (lines 9-31), per-describe `beforeEach` seeding `fetchAllChores` with `makeChore()` (default name `Sweep`), and finds the button via `screen.getByText('+ Add Task')`.
