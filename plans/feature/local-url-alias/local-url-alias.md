# Local URL alias instead of IP:port (F6)

## Summary
Let LAN clients reach chores4irl on the Pi as **`http://c4i.local/`** (mDNS, any
mDNS-capable phone/laptop) and **`http://c4i/`** (router DNS + DHCP search domain, e.g.
Windows/WSL/iOS) instead of `http://192.168.1.214/`. The mechanism is a single Pi-side
change — **rename the Pi's hostname from `MilarachiC4I` to `c4i`** — because both name
systems already in play copy the hostname by default: Avahi (already running on the Pi)
advertises `<hostname>.local`, and the FiOS-style router registers each DHCP client's
hostname in its own `mynetworksettings.com` zone and pushes that search domain to clients.
No app code changes: nginx has `server_name _` and the frontend uses relative `/api` URLs
(proved today by raw-IP access). Deliverables are a reproducible, idempotent host script in
`deploy/pi/` plus its cloud-init drop-in (`deploy/pi/cloud-init/99-c4i-hostname.cfg`),
deploy docs (root `README.md` + `deploy/pi/README.md`), a decision record under
`plans/feature/local-url-alias/research/`, and the rename applied + verified on the live
Pi.

Source contract: `plans/META-PLAN.md` § "F6 — Local URL alias instead of IP:port". User
decision (2026-09-19, during planning): **rename the Pi hostname to `c4i`** (over Avahi
`host-name=` + NetworkManager `dhcp-hostname` knobs, Avahi-only `.local`, or a router
static DNS entry) — fewest moving parts, hostname and mDNS name stay consistent; the user
does not need to keep `MilarachiC4I`. Design decisions DD-1…DD-11 were resolved on
2026-09-19 and are applied below (see `reviews/local-url-alias-review.md` for the options).

## Research Findings
Research was done inline (docs/infra feature, no app modules touched); the Pi and the
laptop were probed read-only over unsandboxed SSH on 2026-09-19. Full write-up lands in
`plans/feature/local-url-alias/research/lan-name-resolution.md` (Step 1).

- **Pi** (`MilarachiC4I`, Debian 13 trixie arm64, user `rmilarachi`, passwordless sudo):
  `avahi-daemon` 0.8 **active** with `libnss-mdns` and `hosts: files mdns4_minimal
  [NOTFOUND=return] dns` — mDNS is already on; `avahi-daemon.conf` has no `host-name=`
  override (advertises the system hostname). No `dnsmasq`, no `avahi-utils`, empty
  `/etc/avahi/hosts` and `/etc/avahi/services/`. NetworkManager active (connection
  `netplan-wlan0-wedonthavewifi` on `wlan0`, DHCP `192.168.1.214/24`, gateway/DNS
  `192.168.1.1`, `ipv4.dhcp-hostname` unset → sends the system hostname);
  `systemd-resolved` inactive; `/etc/resolv.conf` = `search mynetworksettings.com` +
  `nameserver 192.168.1.1`. Docker publishes only `0.0.0.0:80->80` (frontend nginx).
- **Router DNS already resolves the hostname**: from WSL, `getent ahostsv4 MilarachiC4I`
  → `192.168.1.214 MilarachiC4I.mynetworksettings.com` (and an IPv6 AAAA). The router
  learns the name from the Pi's DHCP request (option 12) — this is how `deploy.sh`'s
  `rmilarachi@MilarachiC4I` works today. mDNS plays no part in bare-name resolution, and
  `getent hosts milarachic4i.local` is empty in WSL (no `nss-mdns` there; WSL is in
  `networkingMode=mirrored`, Windows itself resolves `.local` via its built-in mDNS).
- **Hostname is cloud-init-managed and re-applied every boot**: cloud-init 25.2, NoCloud
  from `/boot/firmware`, `cloud-init status` = `degraded done` at the last boot (2026-09-14; the pre-existing `degraded` is the baseline Step 4 records, not an F6 effect);
  `/etc/cloud/cloud.cfg` has `preserve_hostname: false` and runs `set_hostname`,
  `update_hostname`, `update_etc_hosts`; `/boot/firmware/user-data` has `hostname:
  MilarachiC4I` and `manage_etc_hosts: true`; `/var/lib/cloud/data/previous-hostname` =
  `MilarachiC4I`. Consequence: a bare `hostnamectl set-hostname` would keep `/etc/hostname`
  (cloud-init treats a differing `/etc/hostname` as "user maintained") but `/etc/hosts`'
  `127.0.1.1` line would be re-rendered from user-data's `MilarachiC4I` on every boot →
  `sudo: unable to resolve host c4i` noise. **Mechanism (DD-6, option 3 + refinement) —
  three edits, each load-bearing for a different failure mode (numbered in the script's
  `[1/4]` → `[3/4]` execution order):** (1) **user-data precedence caveat:** cloud-init
  merges user-data ON TOP of `/etc/cloud/cloud.cfg.d/*`, so user-data's own
  `manage_etc_hosts: true` would override a drop-in's `false` — hence the script flips
  `manage_etc_hosts: true → false` in `/boot/firmware/user-data` and rewrites its
  `hostname:` line to the new name (so a later `cloud-init clean`, or a re-read of the
  seed, cannot resurrect the old name);
  (2) `/etc/hosts` first, then `hostnamectl` (DD-9 order — hosts first so every `sudo` after `hostnamectl`
  resolves the new name; the single `sudo hostnamectl` call in between resolves the OLD running
  name, which this router's DNS still answers; `raspi-config do_hostname` edits hosts alongside the hostname)
  apply the change now;
  (3) a versioned drop-in `/etc/cloud/cloud.cfg.d/99-c4i-hostname.cfg`
  (`preserve_hostname: true`, `manage_etc_hosts: false`) takes cloud-init out of the
  hostname loop — with `preserve_hostname: true` the `set_hostname`/`update_hostname`
  modules skip, and `manage_etc_hosts: false` makes `update_etc_hosts` a no-op — and it
  is read from `/etc/cloud/cloud.cfg.d/` on every boot whether or not cloud-init re-reads
  the seed. `previous-hostname` is deliberately left as is, matching
  `raspi-config`; with `preserve_hostname: true` the 'assuming user maintained hostname'
  journal line may or may not appear — either is fine. Caveat: cloud-init's NoCloud docs
  say user-data edits normally need an `instance-id` change; whether this Pi's
  `seedfrom: file:///boot/firmware` datasource is re-read on a same-instance reboot
  (expected: yes — no seed dir, so `check_instance_id` returns `None` → cache invalid →
  re-discovery; `CloudConfigPartHandler` is per-always and rewrites
  `/var/lib/cloud/instance/cloud-config.txt`) can only be proven on the Pi — Step 4's
  post-reboot check is the arbiter; the drop-in is the pre-emption, and if the check still
  shows the old name in `/etc/hosts` (cloud-init used its cached config, whose
  `manage_etc_hosts: true` out-ranks the drop-in), a single `sudo cloud-init clean && sudo
  reboot` is the recovery. `user-data` also holds `users:` (password hash) — **never print
  the file; edit those two lines (`hostname:`, `manage_etc_hosts:`) in place only.**
